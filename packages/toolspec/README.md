# @hive-controls/toolspec

The tool-manifest contract: a JSON Schema that a launcher-consumer and any number of
tool-implementers agree on, so neither side has to depend on the other's package.

Every command below is a plain npm script, run from this package's own root. (Inside a
monorepo where this package is a workspace member instead, the same commands take a
`-w packages/toolspec` flag.)

## Who declares, who implements

- **A recipe or tool declares** a `toolspec.schema.json`-conformant manifest describing how to
  launch, configure, and monitor itself (for example, `e2e-doctor`'s own
  `e2e-doctor.toolspec.yaml`).
- **A launcher implements** the contract's read side: [`@hive-controls/formic`](https://www.npmjs.com/package/@hive-controls/formic)
  (`formic run <recipe>`, resolving a declared `env[]` into a launch) and
  [`hivedeck`](https://github.com/hive-controls/hivedeck) (discovery, configuration, monitoring, in
  a terminal UI) both read manifests generically, without depending on any declaring tool's
  internals.

Neither side owns this package: it moves to a launcher's own repo once a third implementer
justifies the split, and the manifest format is versioned independently of both.

## Validating a manifest

```ts
import { validate } from "@hive-controls/toolspec";

const result = validate(manifest);
if (!result.valid) {
  console.error(result.errors);
}
```

`validate` compiles `schema/toolspec.schema.json` with ajv (draft 2020-12) and returns
`{ valid, errors }`; `errors` are `"<instancePath> <message>"` strings.

## Types

`src/types.generated.mts` is generated from the schema by `scripts/codegen.mts` — never hand-edit
it. Regenerate with `npm run codegen`; `npm run check` regenerates to a temp file and exits
non-zero if the committed file has drifted from the schema.

## Conformance fixtures

`fixtures/conformance/{valid,invalid}/*.json` — a would-be implementer (in any language) can
validate their own parser against these and expect the same valid/invalid verdicts this
package's tests assert. See `fixtures/conformance/manifest.md` for what each case exercises.

## Go types

`go/` is a Go module (`github.com/hive-controls/toolspec`) generated from the same
`schema/toolspec.schema.json` — the schema is the single source of truth for both languages.

```go
import toolspec "github.com/hive-controls/toolspec"

var manifest toolspec.ToolManifest
if err := json.Unmarshal(data, &manifest); err != nil {
    // rejects missing required properties, wrong types, and a wrong `toolspec` version
}
```

`go/toolspec.gen.go` is generated by [`go-jsonschema`](https://github.com/atombender/go-jsonschema)
(pinned as a tool dependency in `go/go.mod`) — never hand-edit it. Regenerate with
`go generate ./...` from `go/`; `npm run check` also runs a Go drift check (runs that same
`go generate ./...` directive and byte-compares its output against the committed file) alongside
the existing TypeScript one.

`Unmarshal`ing into `ToolManifest` is **not** a substitute for schema validation, and never rely on
it as one: like plain `encoding/json`, it does not enforce `additionalProperties: false`, and JSON
`null` for an optional field unmarshals to a nil pointer without error even where the schema's
`type` doesn't allow null. `npm test` (and `go test ./...` in `go/` directly) runs a
conformance test against `fixtures/conformance/` that
always validates against `schema/toolspec.schema.json` directly with
[`santhosh-tekuri/jsonschema/v6`](https://github.com/santhosh-tekuri/jsonschema) — the sole source
of truth for whether a manifest is actually valid — regardless of what the struct alone accepts.

Both npm scripts require a Go toolchain on `PATH` and fail loudly (naming the install step) rather
than silently skipping when it's missing.

## v1.1 (additive)

Three optional top-level fields, added without moving the version gate — every v1 manifest with
none of them still validates unchanged, and `toolspec: 1` is still the only accepted value:

- `env`: the environment variables this tool reads — `[{ name, description?, secret?, required?,
default? }]`, `name` matching `^[A-Z][A-Z0-9_]*$`. Lets a launcher know which keys to prompt
  for/resolve and which to treat as secrets, without guessing from source.
- `outputs.evidenceDir`: the name of an `env` entry above whose resolved value is the directory
  this tool writes its evidence into.
- `exit`: this tool's exit codes and what each means, e.g. `{ "0": "passed", "1": "needs-human" }`.

See `fixtures/conformance/valid/env-outputs-exit.json` for a manifest exercising all three, and
`fixtures/conformance/invalid/bad-env-name.json` for the rejected shape.
